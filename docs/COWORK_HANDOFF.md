## 1. What this project is

Curator Bot v1.1 is a **zero-API-cost Telegram bot** that grades a user's photos and generates
**platform-specific text** for 6 platforms: Instagram, Facebook, Tinder, Bumble, Hinge, LinkedIn.

- **3-tier grading.** Tier 1 = local pre-filter (Pillow resolution, OpenCV Laplacian blur + Haar
  faces, imagehash pHash dedup). Tier 2 = deterministic per-platform fit scoring from
  `platform_weights.yml`. Tier 3 = Groq Llama 4 Scout vision (4-axis JSON) for photos that pass the
  local gate, with BLIP-2 scene description + HF Serverless fallback. Tiers 1+2 make **zero** network
  calls; Tier 3 runs **only** on eligible photos to protect the free-tier call budget.
- **Captions vary by platform** — not always a "caption": post_caption (IG/FB), dating_bio
  (Tinder/Bumble), prompt_answer (Hinge, from a fixed 10-prompt library), linkedin_post (LinkedIn).
  Generated by Groq Llama 3.3 70B.
- **Zero variable cost** at MVP scale (free-tier APIs + local libs).

Runtime components (products of the build): BotAgent, SessionAgent, GradingAgent, CaptionAgent,
RankingAgent.

## 2. The dev process (binding) — 8 agents

From `docs/dev_agents_v1.1.md`: **7 sequential stage agents A0→A6** (each owns one PRD roadmap
stage S-00→S-06 and consumes the previous agent's verified output) + **1 independent Reviewer R**.

**Governance rules (binding on every agent):**
1. **KB hygiene** — the repo retains only durable source-of-truth (spec docs, config schemas,
   `requirements.txt`, `.env.example`, the gate checklist, source under VCS). Never commit generated
   captions/outputs, photo test batches, transient logs, model-weight caches, real `.env`, or scratch
   notebooks.
2. **Review-and-test before every push to production.** No stage agent's output lands until its
   Review & Test gate passes: (a) tests green + the PRD's stage-specific assertions present and
   exercised, (b) an independent diff review by **Agent R**, (c) the PRD **Exit gate**. Merge
   authority belongs to R alone — stage agents open changes; they do not land their own work.

**Why R must be a separate invocation.** The process doc is explicit: if A0–A6 and R share one
context, R's independence is nominal ("same context = self-review wearing a reviewer's hat"). So **R
is always spawned as a fresh sub-agent given only the diff + the stage's PRD gate + the standing
checklist** — never the builder's context.

## 3. Orchestration model (how to run a stage)

The orchestrator (you) drives this loop for each remaining stage:

1. **Spawn the stage agent** (general-purpose sub-agent) with the Stage-Agent brief (template in §5),
   filled in for that stage from the PRD. It builds, tests, and commits on the branch — but **does
   not push**.
2. **Spawn Reviewer R** as a *fresh* sub-agent (template in §6) given only the new commit hash, the
   stage's exit gate, and the standing checklist. R independently re-runs `pytest`, reviews the diff,
   and returns **VERDICT: PASS** or **REJECT** (with itemized fixes).
3. **On PASS:** push the commit to the branch (`git push origin claude/sub-agents-build-1k1fez`,
   retry w/ backoff on network errors). Update the PR checklist. Proceed to the next stage.
   **On REJECT:** hand R's itemized fixes back to the stage agent (a new invocation), then re-gate.
4. **A6 is the credentials checkpoint** — pause and get real secrets from the user before any
   production push / deploy (see §8).

Sandbox reality: no live `GROQ_API_KEY` / `TELEGRAM_TOKEN` / `HF_TOKEN`, no BotFather, and
groq/transformers/torch/cv2 may be absent. Every stage is therefore architected so **all logic is
unit-tested with mocks/injected clients**, and live calls sit behind smoke tests that `pytest.skip`
when keys/libs are missing. Never commit secrets — only `.env.example` placeholders.
